# 项目流程宪法

- 版本：1.0
- 批准日期：2026-10-31
- 适用范围：`homebrew-api-starter` 的非平凡业务功能
- 上位约束：[AGENTS.md](../AGENTS.md)、[架构说明](../docs/architecture.md)、[工程说明](../docs/engineering.md)

本宪法只定义**功能如何被规格化、计划、验证和收敛**，不重复 Go、API、数据库、鉴权、审计等工程规则。出现冲突时，以 `AGENTS.md` 和 `docs/` 为准。

## 核心原则

### 1. 现有工程约束优先

规格和计划不得覆盖项目已有的架构边界、路由契约、安全约束、迁移规则、文档更新义务和测试门禁。发现冲突时停止并记录，不得静默绕过。

### 2. 非平凡功能先规格后实现

满足以下任一条件的功能，在 `spec.md` 评审通过前不写业务实现：

- 涉及两个以上独立用户故事
- 涉及 API、数据模型、权限、审计或多角色流程
- 需要跨会话完成
- 存在会影响验收的产品或交互歧义
- 失败代价较高（鉴权、资金、数据删除、生产迁移）

纯修复、格式化、单文件重构和工具链升级不强制走本流程。

### 3. Spec 只回答 What / Why

`spec.md` 定义问题、用户故事、验收场景、非目标、约束和成功指标。技术栈、目录设计、表结构、接口实现细节属于 `plan.md`。

### 4. 垂直切片

每个 P1/P2 用户故事应能独立实现、独立验证、独立演示。拒绝无法追溯到用户价值的投机性范围。

### 5. 歧义显式化

未解决的产品、权限、数据或兼容性问题必须标为 `[NEEDS CLARIFICATION]`，并在进入实现前解决。不得用实现猜测替代产品决策。

### 6. 证据驱动完成

功能完成必须包含可复现的验收证据：测试结果、命令输出、迁移结果或明确的人工验证记录。没有证据的“已完成”不算完成。

### 7. 框架变更同步文档

功能中若引入非业务层框架变更，必须同时遵守 [AGENTS.md 的文档矩阵](../AGENTS.md#31-强制文档更新矩阵)，并更新 [docs/changelog.md](../docs/changelog.md)。

### 8. 历史规格冻结

已验收的 feature 目录是历史记录。后续需求变化创建新的编号，并在新 spec 中标注 `Supersedes`；不静默改写已验收 spec。

## 状态

```text
Draft → Clarified → Planned → Implementing → Verified → Superseded
```

只有 `Verified` 才能关闭功能；`Superseded` 只用于已被新 spec 替代的历史目录。

## 评审门禁

1. `spec.md` 完成后，人工审阅目标、非目标、P1 故事和验收场景。
2. `plan.md` 完成后，人工审阅技术方案、文件影响、迁移、测试和文档义务。
3. 每个 P1 故事实现完成后，人工验收该故事。
4. `verification.md` 完成后，确认所有 acceptance scenarios 有证据。
5. 涉及数据库迁移、鉴权、审计或删除操作时，必须额外记录回滚/恢复方式。

## 不采用的 Spec Kit 默认项

- 不采用 Library-First、CLI-First 作为本项目原则。
- 不强制所有任务 TDD。
- 不要求每个功能走完 9 个 `/speckit-*` 阶段。
- 不把流程宪法复制成第二份工程规范。
- 不为了填模板而创建实施细节或虚构约束。
